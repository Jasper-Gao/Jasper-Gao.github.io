## 作者摘要

计算机已成为各个科学领域不可或缺的工具，但大多数研究人员从未接受过科研计算方面的基本训练，而实验室工作通常有这样的训练。因而，数据可能丢失，分析可能比实际所需耗时更长，研究人员也难以充分发挥软件和数据的作用。计算工作流程也应像实验项目和实验记录一样，把数据整理好，记录各个步骤，并让项目的组织方式便于复现。刚接触科研计算的人往往不知道从何开始。本文介绍一套研究人员可以采用的计算实践，无论他们当前的计算技能如何。这套做法涵盖数据管理、编程、同事协作、项目组织、变更跟踪和稿件写作，来自众多已发表的资料、我们的日常经验，以及我们在志愿组织里的工作。这些组织从 2010 年起已为超过 11,000 人开办过工作坊。

## 概述

我们提出一套每位研究人员都可以考虑采用的计算工具和方法。这些建议来自我们自己的工作、过去六年间数千名 Software Carpentry 和 Data Carpentry 工作坊参与者的经验，以及其他各类指南。我们主要面向刚开始做科研计算的人。

## 引言

三年前，一群参与 Software Carpentry 和 Data Carpentry 的研究人员发表了《科学计算的最佳实践》[1]。那篇论文针对的是已经在研究中进行大量计算的人。随着计算成为所有研究人员都离不开的手段，越来越多人开始接触科学计算，随之而来的问题是该从哪里开始。

本文着眼于容易上手的技能和思路，也就是科学计算中「够用」的实践。我们认为，每位研究人员都值得考虑采用这套基本工具和方法。它们借鉴了许多资料 [2–8]、我们自己的经验，以及过去六年间数千名 Software Carpentry 和 Data Carpentry 工作坊参与者的经验。

我们面向独立开展研究或只有几位合作者的研究人员，项目周期从几天到几个月。入选的做法必须已经有很多人在用，并且有很多人在尝试几个月后仍然坚持使用。加入第二个条件，是因为一项建议只有真正能被采用才有意义。

许多建议都能帮到每位研究人员最在意的合作者，也就是未来的自己。用一句玩笑话来说，三个月前的你可不会回邮件。改变习惯很难，如果收益迟迟不足以抵偿付出的努力，研究人员很可能回到旧做法。因此，本文暂且略过代码审查等我们认为对大规模开发不可或缺的实践，后文会再谈到它们。

我们把建议分成以下六个方面。

- **数据管理。** 保存原始数据和中间数据，记录所有步骤，整理出易于分析的规整数据。
- **软件。** 编写、组织和共享分析用到的脚本与程序。
- **协作。** 让现有和新加入的合作者都容易了解项目并作出贡献。
- **项目组织。** 整理项目的数字文件，方便查找和理解。
- **变更跟踪。** 记录项目各部分随时间发生的变化。
- **稿件写作。** 让写作过程留有记录，尽量减少手工合并冲突。

## 1. 数据管理

项目数据从最初收到的内容到真正用于主要分析的版本，可能需要以多种形式存在。我们的建议围绕两点展开。第一，逐步把数据处理到可以分析的状态，并记录中间数据和处理过程。第二，了解「规整数据」（tidy data）的关键特征，以便加快分析 [5, 8]。

### 1a. 保存原始数据

只要可行，就按数据产生时的样子保存下来，例如保留仪器输出或问卷调查的原始记录。清洗后覆盖原始文件很省事，但忠实保留原始数据，才能从头重跑分析，在分析出错后恢复，并放心尝试不同做法。可以把文件权限改为只读，或使用电子表格的保护功能，降低误改数据、一时冲动手动编辑的可能性。

有些数据用这种方式并不实际。例如，大型、稳定的数据库通常没必要在本地复制一份。这时要记下获取原始数据的确切步骤，以及官方版本号、下载日期等相关信息。

### 1b. 将原始数据备份到多个地点

如果使用外置硬盘，应将备份盘放在原数据存放地点之外。大学往往有自己的数据存储方案，可以咨询校内 IT 部门或图书馆。Amazon S3、Google Cloud Storage 或 Microsoft Azure 等云服务也是价格合理、可靠的选择。对于存储和传输成本较高的大型数据集，可能需要增量备份或专用存储系统。所在机构的 IT 部门和图书馆通常可以帮你了解当地有哪些选择。

### 1c. 把数据整理成你希望收到的样子

想象一下什么样的数据集最方便接手，再把数据整理成那个样子。此处的目标是让人和程序都容易读取数据，应把大幅筛选数据和加入外部信息留给后续步骤。机器可读的数据可以用程序自动处理，当别人想复用你的数据时，这一点尤其重要。我们建议在分析开始时做以下无损整理。

- **文件格式。** 将封闭的专有格式转换成开放的非专有格式，以便日后用不同的计算环境读取 [9]。表格数据可用 CSV，节点和边组成的图等非表格数据可用 JSON、YAML 或 XML，某些结构化数据也可用 HDF5。
- **变量名。** 把晦涩的变量名和人为编码换成含义明确的写法。例如，将 `name1` 和 `name2` 改为 `personal_name` 和 `family_name`，将处理状态的 `1` 和 `2` 改为 `untreated` 和 `treated`，把 `-99` 之类人为约定的缺失值改用许多编程语言表示缺失数据的 `NA` [10]。
- **文件名。** 把特别有用的元数据放进文件名，同时维持统一的命名格式，方便按规则匹配。例如，`2016-05-alaska-b.csv` 让人和程序都方便按年份或地点筛选文件。

### 1d. 让数据便于分析

规整数据可以大幅降低分析难度 [5]。其中有两条关键原则。

- **每列一个变量。** 两个变量各用一列。例如，将 `male_treated` 拆成性别和处理状态。对于 `3.4kg` 这样的值，把 `3.4` 保存在数值列，单位另存一列或写入元数据。
- **每行一次观测。** 为了方便录入与人工检查，数据常以宽表呈现。想象每行是一个采样地点，接下来的各列是不同时间点的测量值。可以把这些列归并到一个测量值变量中，再新增一个时间变量。图 1 展示了这类转换。

### 1e. 记录处理数据的每一步

数据处理和统计建模、推断一样，都是分析的组成部分。只有完整记录处理过程，自己和其他人才能重复分析。

最好的做法是为处理数据的每个阶段编写脚本。初时可能觉得慢，练习后会快起来。眼前的收益是新数据一到，就能轻松重做数据准备。这些步骤也可以在以后的相关项目里复用。处理体量很大的数据时，数据准备还可能包括编写并保存从远程存储获取完整数据或其子集的脚本。

OpenRefine 等清洗工具有图形界面，也能自动记录每一步。当这类工具和脚本都用不上时，要把每项手工操作写清楚，例如使用了哪个菜单、复制粘贴了哪一列、点了哪个链接。有时很难完整记录原因，但至少可以记录做了什么。例如，在图像中选定感兴趣的区域，本身就是交互操作，但可以把选定区域保存成一组边界坐标。

### 1f. 为使用多张表做好准备，为每条记录设置唯一标识符

原始数据即便整理得很规整，也可能需要补充其他信息。例如，主表按受试者 ID 记录各人在静息和体力负荷之后的心率，年龄、性别等人口统计变量则放在第二张表中，需要通过合并或查找来补充。如果两张表的受试者 ID 都用统一格式，例如一律写 `14025`，避免出现 `14,025` 和 `014025` 混用，合并就容易得多。通常应为每条记录或每个观测单位指定唯一、持久的键。两个数据集里的变量如果指同一件事，也要采用相同的名字和编码。

### 1g. 将数据提交到可信、能签发 DOI 的存储库

数据和论文一样是研究成果，对他人可能同样有用，甚至更有用。Figshare、Dryad 和 Zenodo 等存储库可以让他人发现、使用和引用你的成果。许可证在第 3 节讨论。提供元数据时，请遵守所在研究领域的标准。

元数据分两类，一类描述整个数据集，另一类描述数据集里的内容。面向人时，用方便阅读的方式编写 `README` 等元数据。如果读者还包括自动采集元数据的程序，就填写正式的元数据字段，同时写一份便于人阅读的 `README` [11]。

按顺序采用上述做法，会逐步得到更干净、更贴合具体任务的中间数据文件。另一种做法是把全部数据管理步骤塞进一套完整的分析程序，在运行时临时生成中间产物，只保存在内存里。如果项目只需要少量清洗或加工，这样做有时也合适。我们建议显式生成并保存中间产物。这样便于单独重跑流水线的一部分，再回头检查和改进某个数据处理步骤。把漫长的流程拆成几部分，也更容易理解、共享、描述和修改。数据集越大，整份存储或传输越费资源，这种做法的好处就越明显。

## 2. 软件

如果你或你的团队正在写数万行软件，供数百位素未谋面的人使用，你所做的就是软件工程。如果只是偶尔写几十行代码，而且很可能只有自己用，几项软件工程的基本做法也能让工作轻松些，还能让别人更容易理解和复用你的代码。

可读、可复用、可测试，都是模块化代码带来的好处。模块化就是用简短、用途单一、输入和输出明确的函数来组成程序 [12]。关于这一点已有大量论述 [12–14]，本节挑选了容易采用、也能给你和合作者带来收益的做法。

### 2a. 在每个程序开头写简短的说明性注释

程序再短也值得写。注释至少应包含一个用法示例，好的例子胜过千言万语。条件允许时，也应说明参数的合理取值。下面是一例。

```text
合成图像文件，用于测试圆度估计算法。
用法：make_images.py -f fuzzing -n flaws -o output -s seed -v -w size

-f fuzzing  斑块的模糊程度范围（通常为 0.0–0.2）
-n flaws    决定每个样本瑕疵数的成功概率（例如 0.5–0.8）
-o output   输出文件名
-s seed     随机数生成器的种子（较大的整数）
-v          显示详细输出
-w size     图像宽度和高度，单位为像素（通常为 480–800）
-h          显示帮助信息
```

### 2b. 将程序拆成函数

把每个函数控制在一页以内，约 60 行。函数是一段可以复用的代码，其余程序可以把它当成黑箱。定义函数的语法因语言而异，但通常要给它起名，列出输入参数，并说明它会产出什么。函数的输入参数最好不超过五六个，所需信息应从参数传入。

这样做是为了照顾最有限的内存，也就是人的记忆。人的短期记忆通常一次只能容纳七项左右的信息 [15]。把软件拆成认知负担小的片段，再用这些片段组成程序，我们才容易理解它的行为。函数也让测试和排查问题更方便。

### 2c–2e. 消除重复，查找并测试已有库

**2c.** 把重复代码写成函数后复用，避免复制粘贴。用列表一类的数据结构来组织彼此关联的数据，例如用 `score = (1, 2, 3)` 管理三项分数，避免创建 `score1`、`score2`、`score3` 三个变量。

**2d.** 自己动手写之前，先找找有没有仍在积极维护、能完成任务的库。各种编程语言都有可导入的库，别人的代码已打包好，可用于统计、建模、绘图等众多用途。许多语言有集中的软件库索引，例如 R 的 CRAN 和 Python 的 PyPI。

**2e.** 在正式依赖一个库之前，先测试它。

### 2f. 给函数和变量起有含义的名字

名字既能说明用途，也能让程序更好读。一般来说，变量的作用域越大，名字就应该越清楚。循环计数器用 `i` 或 `j` 就可以，但反复使用的内容，例如程序的主要数据结构，应该有更明确的名字。也应遵循语言自己的命名约定，例如 Python 里用 `net_charge`，Java 里用 `NetCharge`。

**Tab 补全。** 现代文本编辑器几乎都支持按 Tab 补全。输入变量名的开头，再按 Tab，就能填入完整名字。用上补全功能后，较长而明确的名字也很容易输入。

### 2g. 明确写出依赖与运行要求

这通常以项目为单位记录。例如，在项目根目录添加 `requirements.txt` 一类的文件，或在 `README` 里添加「入门」一节。

### 2h. 用条件语句控制程序行为

靠注释掉和恢复不同代码段来切换程序行为，很容易出错，也会使自动化分析难以实现。用程序中的 `if`/`else` 控制程序执行哪些步骤。

### 2i. 提供简单示例或测试数据集

这样用户，包括你自己，就能检查程序能否正常运行，以及对简单的已知输入能否给出已知的正确输出。这种构建后的「冒烟测试」尤其适合在改动看似无关紧要，或者程序需要在开发者的笔记本和院系的计算集群等多台机器上运行时使用。

### 2j. 将代码提交到可信、能签发 DOI 的存储库

投稿时，像存档数据一样存档代码。软件也是研究成果，应该和论文一样方便他人引用和注明作者。Figshare 和 Zenodo 都为软件提供 DOI，Zenodo 也能直接与 GitHub 集成。

## 3. 协作

项目可能从一个人开始，也可能从少数熟悉的合作者开始。设计项目时就应该考虑如何让新合作者顺利加入。新加入的也许是实验室的研究生或博士后，也可能是搁置一段时间后重新接手项目的你。正如文献 [16] 所总结的，你要让他们容易搭建本地工作环境，知道有哪些任务可做，也清楚该如何提交贡献。同时，也要让别人容易注明你的贡献。

### 3a. 写一份项目简介

在项目根目录放一份简短文件，说明项目的目的。这个文件一般叫 `README` 或 `README.txt`，应包括项目标题、简要描述、最新的联系方式，以及一两个运行数据清洗或分析任务的例子。它往往是用户和合作者先看到的文件，所以要写清楚你希望他们怎样参与。如果希望招募合作者，就明确表示欢迎，告诉他们去哪里看许可证、有哪些地方可以帮忙。

还应提供 `CONTRIBUTING` 文件，说明怎样运行、使用项目或提交贡献。可以列出要安装的依赖、用于确认安装成功的测试，以及项目遵循的指南或检查清单。

### 3b. 建立共享待办清单

可以用名为 `notes.txt` 或 `todo.txt` 的纯文本文件，也可以在 GitHub 或 Bitbucket 等网站上为每项待办创建一个议题。还可以用「容易上手」之类的标签标出适合新手的任务。无论选择哪种工具，都要把待办写到新加入的人也能看懂。

### 3c. 约定沟通方式

明确团队成员彼此之间，以及与外部用户或合作者之间的沟通方式，并在适当时公开。约定内容包括邮件列表、聊天频道、语音或视频会议、文档和会议纪要的位置与所用工具，以及哪些渠道公开、哪些保持私密。

### 3d. 明确许可证

在项目根目录提供 `LICENSE` 文件，明确项目的软件、数据和稿件分别适用哪些许可证。作者未明示许可时，默认保留全部权利，其他人无权擅自复用或修改材料。

对于数据和文本，我们建议采用知识共享的 CC0 或 CC BY。CC0 用于放弃保留权利，CC BY 允许共享和复用，并要求注明创作者。对于软件，我们建议采用 MIT、BSD 或 Apache 等宽松的开源许可证 [17]。

**选择许可证时应避免的做法。** 我们建议避开附带「非商业性使用」条款的知识共享许可证，因为它可能妨碍某些复用。例如，一位来自发展中国家的研究人员受政府委托、有偿编写公共卫生报告，如果你的数据限于「非商业性使用」，她就没法在报告中使用这些数据。我们偏好宽松的软件许可证，因为这类许可下的软件更容易集成到其他项目中。关于它们与 GNU 通用公共许可证（GPL）的差别，见文献 [17] 第 3 章。

### 3e. 让项目易于引用

在项目根目录放置 `CITATION` 文件，说明如何引用整个项目，如何找到并引用各自具有 DOI 的数据集、代码、图表和其他成果。以下是 The EcoData Retriever 的 `CITATION` 文件示例。想看更详细的例子，可以参阅 khmer 项目。[The EcoData Retriever](https://github.com/weecology/retriever) · [khmer](https://github.com/dib-lab/khmer)

> 请按以下格式引用本项目。
>
> Morris, B. D. and E. P. White. 2013. “The EcoData Retriever: improving access to existing ecological data”. *PLoS ONE* 8:e65848. [DOI](https://doi.org/10.1371/journal.pone.0065848)

## 4. 项目组织

用清晰、一致的目录结构管理构成项目的文件，有助于自己和别人追踪这些文件。我们的建议主要来自文献 [2, 3]。

### 4a. 每个项目使用以项目命名的独立目录

把研究工作划分成不同项目，与判断一段代码是否应提取成函数类似，最终目的都是让自己和别人能看懂你的工作。有些研究人员为每篇正在写的稿件建一个项目，另一些人则把使用相同主题、数据集或算法的工作归为一个项目。

可以根据数据和代码的重叠程度划分项目。如果两项研究完全不共享数据或代码，通常分开管理最省事。如果它们共享超过一半的数据和代码，通常适合放在一起。如果某个工具会被多个项目使用，共用代码最好单独成为一个项目。项目往往有各自的组织需求，以下建议适用于数据、代码、分析产物和其他文件的基本组织。按文件类型归类，并保持一致，以后就容易找到并使用这些文件。

### 4b. 把项目文档放进 `doc/`

这里包括稿件、源代码文档，以及记录实验的电子实验笔记。大型项目可以为这些不同类型的文件分别建子目录。

### 4c. 原始数据和元数据放进 `data/`，清洗与分析产物放进 `results/`

生成的文件包括清洗过的数据集和模拟数据等中间结果，也包括图表等最终结果。除了最简单的项目，`results/` 通常还要分子目录。清洗后的数据、统计表和可用于发表的最终图表，应采用清晰的命名规则或分别放在不同子目录中。属于同一篇论文或同一出版物的结果应放在一起。同理，`data/` 中也可能需要子目录，按时间、采集方法或与分析最相关的其他元数据来组织原始数据。

### 4d. 把项目源代码放进 `src/`

`src/` 保存为项目编写的所有代码。这里包括用 R、Python 等解释型语言写的程序，用 Fortran、C++、Java 等编译型语言写的程序，也包括 shell 脚本、从数据库提取信息的 SQL 片段，以及重建结果所需的其他代码。

这个目录可能包含两类文件，可以用明确的文件名或子目录将它们区分开来。第一类是执行核心分析的文件或文件组，例如数据清洗和统计分析代码。它们承担项目最核心的科研计算。

第二类是控制脚本，也叫驱动脚本。它把整个项目从头到尾的分析步骤串起来，给出具体参数和输入输出命令。例如，一个简单项目可能会读取一张原始数据表，从目录中的其他文件导入若干清洗和分析函数，最后生成并保存数值结果。如果小项目只有一个主要产物，可以在 `src/` 下面放一个驱动脚本，取 `runall` 之类一眼就懂的名字。框 2 是一个典型示例。它用一个 `TEMP_DIR` 变量避免重复写同一个目录名。

**框 2　`runall` 脚本示意，沿用原文命令写法。**

```text
TEMP_DIR = ./temp_zip_files
echo "打包分析工具所需的 ZIP 文件……"
mkdir $(TEMP_DIR)
./src/make-zip-files.py $(TEMP_DIR) *.dat
echo "正在分析……"
./bin/sqr_mean_analyze -i $(TEMP_DIR) -b "temp"
echo "正在清理……"
rm -rf $(TEMP_DIR)
```

### 4e. 把编译好的程序放进 `bin/`

`bin/` 放的是从 `src/` 中的代码编译出的可执行程序。`bin` 来自 Unix 的旧命名惯例，源于英文 *binary*。只有项目用到从 `src/` 编译出来的可执行程序时，才需要这个目录。

**脚本与程序。** 这里的「脚本」指可直接执行的文件，「程序」指使用前需显式编译的文件。这更像是程度上的差异。例如，Python 库在加载时其实会编译成字节码。也可以从编辑方式理解，脚本可直接编辑，而编译后的程序需要通过修改源代码来更新。

**外部脚本。** 如果 `src/` 存放人可读的源代码，而 `bin/` 存放编译后的二进制文件，可以直接执行的脚本该放哪里，尤其是从外部引入的脚本？一方面，它们可能与 `src/` 里的项目脚本使用同一种语言。另一方面，它们也像 `bin/` 里的程序一样可以执行。两处都可以，团队各项目使用同一个规则即可。和文中许多其他建议一样，一致性和可预期性更重要。

### 4f. 用反映内容或用途的方式命名文件

可以用 `bird_count_table.csv`、`manuscript.md` 或 `sightings_analysis.py`。尽量避免用连续编号，如 `result1.csv`、`result2.csv`，也尽量避免用文件在最终稿件里的位置命名，如 `fig_3_a.png`。项目一变，这些数字几乎肯定也会变。

框 3 展示了如何将这些建议用到一个简单项目上。根目录的 `README` 提供项目概况，`CITATION` 说明如何引用，`LICENSE` 说明许可条款。`data/` 中有一份记录鸟类数量的 CSV 文件，也可以在这里加入机器可读的元数据。`src/` 中的 `sightings_analysis.py` 包含汇总表格数据的 Python 函数，驱动脚本 `runall.py` 载入数据表，调用从 `sightings_analysis.py` 导入的函数，并将汇总表存入 `results/`。

**框 3　项目目录示例。**

```text
.
├── CITATION
├── README
├── LICENSE
├── requirements.txt
├── data/
│   └── birds_count_table.csv
├── doc/
│   ├── notebook.md
│   ├── manuscript.md
│   └── changelog.txt
├── results/
│   └── summarized_results.csv
└── src/
    ├── sightings_analysis.py
    └── runall.py
```

这个项目无需编译软件，所以省去了 `bin/`。`doc/` 中有两份 Markdown 文档，一份是持续更新的实验笔记，记录项目的想法和实现过程，另一份是持续更新的论文草稿，介绍项目发现。

## 5. 变更跟踪

跟踪你和合作者对数据与软件所做的变更，是科研的重要组成部分。在发表前重做分析、回复审稿意见，或给审稿人、编辑和读者提供补充材料时，能定位和取回整个项目的特定版本，有助于复现工作。

我们认为最好的变更跟踪工具，是软件开发中使用的版本控制系统，例如 Git、Mercurial 和 Subversion。它们记录文件改了什么、何时由谁改动，并能把变更同步到共享服务器，让多位贡献者一起管理同一组文件的变化。

这些工具能简化跟踪过程，但上手可能需要一些时间。因此，我们提供两套建议，一套是有章法的手动管理办法，一套使用完整的版本控制工具。可以先用第一套，熟悉后再过渡，也可以直接使用版本控制。

无论采用哪种方法，都建议做到以下几点。

- **5a. 人工创建的内容，几乎都应在创建后立即备份。** 包括各种脚本和程序、项目依赖的软件包，以及文档。下文会介绍几个例外。
- **5b. 控制每次变更的大小。** 改动太大会使变更记录失去价值。例如，一次「修改脚本文件」就增改数百行，会让人难以分辨分析的各部分分别改了什么。拆得太细也不合适。一个实用的判断标准是，这组改动是否有可能在将来被你一次性撤销。
- **5c. 经常共享变更。** 项目成员应定期共享自己的修改，并合入别人的改动。随着各自的版本越差越远，合并需要的工作量会比差异本身增长得更快。下文的手动办法尤其需要注意这一点，因为碰上并行修改造成的冲突时，没有工具帮你合并。
- **5d. 制定、维护并使用保存和共享变更的检查清单。** 清单可纳入这些要求。编写清楚解释变更的日志，约定单次变更的大小和内容，遵守代码风格，更新待办清单，避免提交半成品或有错误的代码。检查清单的实际价值见文献 [18]。
- **5e. 将项目目录同步到工作电脑之外。** 可以用 Dropbox 之类的同步服务，或 GitHub 之类的远程版本库。至少每天同步一次。可能只需要几分钟，而笔记本失窃或硬盘损坏时，这几分钟就值回来了。

### 手动管理版本

第一套办法完全依靠手工操作，还有两项做法。

**5f. 在项目文档目录添加 `CHANGELOG.txt`。** 为每次变更写带日期的记录，按日期倒序排列，最新的放在最前面。它相当于实验笔记，条目可以像下面这样写。

```text
## 2016-04-08
* 将默认插值方法改为三次插值。
* 把有关家族结核病史的问题移到问卷末尾。

## 2016-04-06
* 增加三次插值选项。
* 移除有关葡萄球菌暴露的问题，可从血液检测结果推断。
```

**5g. 每次进行会实质影响结果的变更后，复制整个项目。** 把副本放进同步区域下以日期命名的子目录。项目结构会类似这样。

```text
.
└── project_name/
    ├── current/
    │   └── … 前文所述的项目内容
    ├── 2016-03-01/
    │   └── … 2016 年 3 月 1 日的 current 内容
    └── 2016-02-19/
        └── … 2016 年 2 月 19 日的 current 内容
```

`project_name/` 映射到 Dropbox 一类的外部存储空间。日常工作在 `current/` 中进行，其他子目录存放旧版本。

**存储便宜，时间昂贵。** 很多文件根本没变，全部复制看起来会浪费空间。但按当时的零售价，一块 1 TB 硬盘大约 50 美元，50 GB 的成本不到 5 美元。只要把大型数据文件放在这块备份区域之外，全部复制的成本就低于手动挑拣文件所耗费的时间。

这套方法不用新工具就能满足前述要求。如果多名研究人员共同参与项目，就需要协调好，保证同一时间只有一个人编辑某个文件。可以考虑每位贡献者各维护一个变更日志，并在每次备份时合并这些日志。

### 版本控制系统

上述手动做法最依赖自律。我们自己的项目用的是第二套做法。版本控制工具能加快手工做的事，有些步骤可以自动化，也可以在其他步骤中强制遵守流程，较少依赖自律就能得到更可靠的结果。

**5h. 使用版本控制系统管理项目变更。** 框 4 简要解释了它的运作方式。科研中哪种工具用得最多很难判断，但论文发表时，讨论最多的无疑是 Git。这在很大程度上要归功于 GitHub，它把通过 Git 协作的技术基础与现代网页界面结合起来。GitHub 当时对公开和开源项目，以及学术界和非营利机构的用户免费。GitLab 也广受好评，有人偏好它，因为其平台本身免费且开源。Bitbucket 当时免费托管 Git 和 Mercurial 仓库，但科研用户相对少得多。

**框 4　版本控制系统如何运作。**

版本控制系统在仓库中保存项目文件的快照。用户修改自己的工作副本，想永久记录或与同事分享时，就把变更保存到仓库。系统会自动记下何时、由谁做了哪些修改。

多人同时编辑一个或多个文件时，系统会检测重叠的改动，要求先解决冲突，再保存结果。现代版本控制系统允许仓库之间同步，避免某个仓库成为单点故障。与手动管理相比，工具还有以下好处。

- 只保存按需重建文件旧版本所需的信息，免去反复备份整个项目的工作。
- 自动为保存的变更加上时间戳，无需手工给备份起合适的名字。
- 每次保存变更时提示填写日志，并准确记录实际改了什么。日后出问题时，可以直接查实，不必只凭记忆或日志描述推断。
- 同步到远程存储前检查是否会覆盖别人的工作。如果会，就协助识别冲突并合并改动。

### 哪些文件不适合纳入版本控制

版本控制的收益取决于文件的大小与格式。首先，版本控制系统的文件比较功能主要针对纯文本，例如源代码。查看所谓的「差异」（diff）是它的一大乐趣。Microsoft Office 文件（如 Word 的 `.docx`）或 PDF 等二进制文件也可以存入版本库，但系统通常难以指出两个版本之间具体改了什么。CSV 等表格数据可以纳入版本控制，不过即使实际数据没有变，只是调整了行或列的顺序，也可能产生很大的差异记录。

其次，原始数据理应保持原样，通常无需跟踪版本。如果中间数据文件和其他结果能从原始数据和软件重新生成，也不必把它们放进版本库。如果它们体积较小，则仍建议纳入版本控制，让合作者方便取得它们，也便于比较版本。

最后，作者指出，当时的版本控制系统并非为兆字节、更不用说吉字节级文件而设计，因此应将大型数据或结果文件留在库外。作为尺度参考，原文提到 GitHub 对单个文件设有 100 MB 上限。当时一些新兴的混合系统，例如 Git Large File Storage（LFS），可以跟踪文本记录，同时将大文件放在远程服务器。作者撰文时认为它们还不够成熟，暂未推荐。

### 避免意外共享

对医学数据等依法禁止共享的资料，研究人员应避免将其放入公开版本库。一些机构提供私有版本控制系统，可以向 IT 部门询问。也要留意，别误把密码、私钥等凭证存入他人能访问的版本库。

## 6. 稿件写作

有句老玩笑说，做研究占一个项目的前 90%，写论文占另外的 90%。讨论科学计算时，写作很少被提及，但计算改变了研究，也同样改变了科学写作。

学术写作中常见的一种做法，是由主要作者把一版又一版稿件发给合著者征求反馈。合著者可能直接修改文档、添加批注、在邮件里用纯文本回复，或把三种方法混用。这样大家可以用熟悉的工具，却产生了许多需要追踪的文件，还要费力地手工合并意见，才能得到下一版主稿。

我们建议借鉴软件和数据管理的做法，让写作能容纳更多合作者，并且便于复现。和前文讲版本控制时一样，我们提供两种稿件管理办法。这两种办法都有以下目标。

- 始终只有一份所有合著者都能访问的主文档，自己和他人现在和将来都能找到正文。
- 降低工作丢失或彼此覆盖的可能性。
- 便于跟踪和合并多位合作者的贡献。
- 减少重复录入和手动录入，尤其是在制作参考文献、目录和各种清单时。
- 便于重新生成最终发布格式，例如 PDF，并能判断它是否为最新版。
- 便于与合作者分享最终版本，并向期刊投稿。

**动笔前先约定流程。** 全体作者在动笔前达成一致，比具体采用哪种流程更重要。同时商定一个统一的反馈渠道，例如邮件讨论串、邮件列表、GitHub 或 Bitbucket 的议题跟踪工具，或某种在线共享待办清单。

### 6a. 在线维护一份主稿

第一种做法很多研究人员已经熟悉。用 Google Docs 等支持富文本排版、变更跟踪和参考文献管理的在线工具写稿。文档在线时，所有人的修改集中在一处，无需手动合并。

有些合作者习惯使用带图形界面的桌面编辑器，可能觉得改用在线工具也很麻烦。可以在作出重大修改后，把稿件转换成 Microsoft Word 的 `.docx`、LibreOffice 的 `.odt` 等桌面编辑器格式，下载后放到 `doc/` 中。不过，桌面文档和纯文本来回转换时，现有工具无法总是自动处理修改与建议，因此有些内容仍要手动合并。Pandoc 可以帮上不少忙。

### 6b. 将纯文本文档纳入版本控制

第二种办法像管理软件一样管理稿件。数学、天文学、物理学和相关学科的研究人员已经这样做了几十年。用 LaTeX、Markdown 等可纳入版本控制的纯文本格式写稿，再按需要用 Pandoc 等能通过脚本调用的工具转换成 PDF 等格式。

版本控制系统便于查找和合并多人同时编辑产生的差异，也便于批注和审阅。这种办法复用了管理数据和软件的工具与技能，是走向完全可复现研究的一个起点。它也要求每位贡献者熟悉更多工具，包括 Markdown 或 LaTeX、Make、BibTeX，以及 Git 和 GitHub。

### 为什么给稿件写作提供两种办法？

我们起初建议一律使用纯文本和版本控制来管理稿件，但社区里有几位成员认为，学习这些工具本身就是一道很高的门槛。Stephen Turner 就举过这样一个例子。

> ……试着向一位忙得不可开交的临床合作者解释什么叫编译文档吧。等等，你还得先解释纯文本和文字处理的区别，再解释文本编辑器、Markdown 或 LaTeX 编译器、BibTeX、Git、GitHub，等等。与此同时，手术室正在呼叫这位医生……
>
> ……我们再怎么说服自己，真要和科学计算圈外的人合作时，这套写论文的方法门槛还是太高。出发点再好，最后往往也只剩一句「给我一份打开修订功能的 Word 文档就好」，或者类似的话。

Arjun Raj 也在一篇博文中写道 [19]。

> Google Docs 的长处在于便于分享、协作、同时编辑、添加批注和回复批注。当然，用纯文本系统加版本控制也能实现类似的效果。问题是，为什么会有人想这么做……
>
> 可复现研究的目标是让人能够复现……计算分析。版本控制的目标是跟踪源代码的变化。两个目标本质上不同，虽然有所重叠，但版本控制只是实现前一个目标的一种工具，它带来的额外负担往往让人觉得不值得。

用 Google Docs 一类的工具协作，已经能满足我们一开始列出的要求。纯文本格式还有一些额外好处，其中一点是可以用和其他材料相同的方式，把稿件保存在同一个地方。我们仍然建议避免把 LibreOffice 或 Microsoft Word 等桌面工具与邮件、Dropbox 等文件共享服务搭配使用，因为合作者一多，这种流程就很难维持。

### 补充材料

补充材料往往包含项目中许多重要的工作，例如图表，或对算法、软件、方法和分析的更详细说明。为了便于他人使用，尽量提供 PDF 之外的格式，因为从 PDF 提取数据出了名地困难。我们建议把其他人可能复用的结果，例如表格里的数据、图背后的数据，单独存成 CSV、JSON、YAML、XML 或 HDF5 等文件。比起比较新颖的格式，我们更偏好久经使用的格式，正如那句老话，「用得最久的，往往也最耐久」。补充材料中的命令和代码也一样，应采用最便于复用的格式，例如源代码文件或 Unix shell 脚本。

## 本文略过的实践

我们有意略过了许多好工具和好做法，其中一些我们每天都用。有的必须建立在前文的基本习惯上才有意义，有的则要投入更多才见成效。

- **分支。** 可以把分支想成版本库里的一个「平行世界」。开发者创建分支，以便独立推进同一个项目的多项变更。熟练开发者使用 Git 等工具时常常依赖分支，初学者则需要多理解一层。过去用 CVS 和 Subversion 的程序员很少依赖分支，也能把事情做好。掌握基本的编辑和提交流程后，再引入分支也无需大改既有习惯。
- **构建工具。** Make 一类的工具起初用于重新编译过时的软件组件，现在也用来重新生成数据和整篇论文。当一个或多个原始输入文件有变化时，Make 可以自动重跑受影响的分析，重新生成图表，然后生成依赖它们、供人阅读的 PDF。初学者可以先写 shell 脚本，每次把整个流程重跑一遍。这样可能多做一些计算，但小项目用当时的机器也足以应付。
- **单元测试。** 单元测试是针对软件某项具体功能的小型测试。项目用它来防止回归，也就是保证某处改动不会破坏其他部分。单元测试对大型软件库和程序很重要。就我们的经验而言，独自开展探索工作时，研究人员往往觉得没必要为此投入精力。例如，Noble 的建议 [3] 就没有测试目录。考虑到本文读者实际会采用哪些做法，我们把单元测试留在了清单之外。
- **测试覆盖率。** 现代编程语言都有工具可以报告测试用例覆盖了哪些代码行，也就是哪些行在运行测试时执行了，哪些没有。和单元测试类似，项目规模增长后，这项工作才更容易见到收益。
- **持续集成。** Travis CI 等工具可以在版本库有改动时自动运行用户定义的命令。通常会运行测试，检查原本有效的功能是否仍然有效。可以在保存变更之前测试，失败时拒绝该变更，也可以在保存之后测试，出问题时通知贡献者。对贡献者众多的大项目，持续集成很有价值。在为特定分析编写代码的小项目里，收益通常较少。
- **性能分析与调优。** 性能分析用来测量程序把运行时间花在哪里，是加速程序前的重要一步。程序性能确实成为瓶颈时，这两项工作就值得做。按我们的经验，多数使用者首先需要花更多时间让程序算对。
- **语义网。** 本体及其他正式的数据定义很有用，但按我们的经验，实际工作中连 Dublin Core 这种相对简单的标准也很少遇到。
- **文档。** 好文档是决定软件能否被采用的重要因素。实际工作中，往往有了会使用文档的合作者，人们才愿意写全面的文档。不过，大家很快就能看出在每个脚本开头写一段说明的好处，因此我们建议从这一步做起。
- **参考文献管理工具。** 研究人员应使用 Zotero 等参考文献管理器，也应获取 ORCID，并在发表成果时用它标识自己。关于两者的具体讨论超出了本文范围。
- **代码审查与结对编程。** 多人都在贡献大量代码的项目会从这些做法中受益。本文面向的读者通常没有在这样的项目中工作 [20]。

许多经验丰富的程序员即使做小项目，也会采用其中一些甚至全部做法。这对他们很合理，因为他们已经学会了工具，放到下一个项目里只需少量时间。他们也明白，项目规模扩大后可能会用到其中某些做法，不妨及早准备。

问题出现在有经验的人向尚未掌握工具的人提建议时。初学者还没有体会到项目扩大后这些做法能节省多少时间。此时一下子建议上单元测试、覆盖率检查和持续集成，很容易让人觉得无从下手。

## 结论

我们介绍了一系列科学计算实践，依据的是我们共同积累的经验，以及我们通过 Software Carpentry、Data Carpentry 和类似组织接触的数千位研究人员的经验。这些做法讲求实用，刚接触计算的人也容易上手，个人和团队都可以采用。它们能让研究人员用更少的时间和精力完成更多工作，也能让计算工作更容易复现，进而加快整个研究领域的进展。如今几乎所有研究都越来越依赖计算。

要取得进展，还需要有人推动。期刊和资助机构的要求正在为这些实践提供越来越多的激励，但真正落实它们所需的时间和技能，仍未得到应有的重视。

在实验室层面，课题负责人（PI）能发挥最大的作用，可以要求实验室的研究遵循这些建议。即使没有计算背景，负责人也可以要求学生在组会展示代码、与同组成员共享代码，确保组员可以获取和使用数据，并把计算方法写完整。负责人还可以认可做好这些事所需的时间，提供培训机会。

大学也可以提供支持。这类帮助通常来自 IT 部门或高性能计算（HPC）团队，研究图书馆员则是常被忽视的资源。早在这些计算问题出现之前，图书馆员就已经在研究和处理数据及其来源。越来越多的大学也设置了专门服务研究人员的数据馆员岗位。

许多校园里有学生自发组织的互助学习小组。它们可以独立运作，也可以与 Software Carpentry、Data Carpentry 或 The Hacker Within 等组织合作。

最后，许多资助机构现已要求提供数据管理计划，并开展教育和外展活动。执行这些计划的实际成本包括培训。要求研究人员做这些事，却没有教他们怎么做，既不公平，也不利于落实。资助方应该开始投资这类培训。我们希望这些建议有助于大家就何为「够用」、怎样才能做到「够用」形成共识。
